# Ledger

팀 프로젝트의 지출을 기록하고, 검산 가능하게 정산하고, 하나의 공동 장부로 남기는 서비스.
Master Context 문서(`ledger_master_context.md`)가 제품 의사결정의 기준이다.

```
lib/domain/       정산 엔진 — 프레임워크·DB·UI에 의존하지 않는 순수 함수
lib/db/           DB ↔ 도메인 매핑과 저장소
lib/access.ts     초대 토큰 검증과 접근 제어
app/              Next.js App Router — 화면과 서버 액션
supabase/         마이그레이션 6개 + 스키마 가드 테스트 25개
scripts/          정산 시뮬레이션, 프로토타입 빌드
prototype/        단일 파일 UI 프로토타입 (엔진 인라인 포함)
```

## 실행

```bash
npm run simulate          # 정산 시뮬레이션 + 불변식 23개 검산 (의존성 없이 Node만으로)
npm run prototype         # 프로토타입 HTML 다시 빌드
npm run dev               # 앱

supabase db reset                                # 마이그레이션 8개 적용
psql -d <db> -f supabase/tests/guards_test.sql   # 스키마 가드 테스트 25개
```

곁에 있는 문서 두 개. 어느 코드도 이것들을 import 하지 않지만 지우면 안 된다.

- `setup-guide.html` — Supabase·구글·카카오·배포까지 처음부터 따라 하는 설치 안내서.
  브라우저로 열어서 본다.
- `character-guide.html` — 길잡이(§21.10)의 자세와 말투를 정리한 문서.

## 확정된 결정

| 주제 | 결정 | 이유 |
| --- | --- | --- |
| 정산 후 지출 수정 | 원본 보존 + 보정 항목 | 확정된 정산 숫자가 영원히 안 바뀐다. 왜 보정됐는지가 장부에 흔적으로 남는다 |
| 환불 | 음수 금액 지출 | 엔진 수정 없이 부분 환불까지 처리된다. 언제 얼마가 돌아왔는지 남는다 |
| 팀원 변동 | 지출마다 기록 시점 명단을 저장 | 나중에 팀원이 늘어도 과거 지출이 다시 안 나뉜다 |
| 부가 금액 (배송비·할인) | 지출 금액에 합산 | 캡처 한 장으로 끝나는 입력 흐름을 유지 |
| 스택 | Next.js + Supabase | Postgres·인증·이미지 저장소를 한 번에. 서버에서 AI 호출 |
| 참여 방식 | 생성자만 로그인 + 초대 링크 | 팀원 전원 가입이 도입의 가장 큰 마찰 (§5.2) |
| AI 입력 | 서버에서 호출 + 팀당 월 상한 | 건당 약 4원. BYOK를 붙이는 비용이 API 비용보다 훨씬 크다 |
| 로그인 | 이메일 + 카카오 | Supabase Auth가 둘 다 지원. 카카오 이메일 수집은 비즈앱 전환이 필요하므로 이메일 없이도 계정이 서게 설계 |
| 송금 | 앱 밖에서 사람이 하고 받은 사람이 확인 | 카카오페이·네이버페이는 외부에 P2P 송금 API를 주지 않는다 |
| 정산 공유 | 카카오톡 공유 | 검수 없이 쓸 수 있고 보낼 채팅방을 사용자가 고른다 |
| 첫 화면 | 빠른 N빵 + 로그인 | 접속하자마자 계산이 되고, 남기고 싶을 때 로그인한다 |
| 시각 | 순수한 웹의 검정·흰색·파랑 | 종이 질감이나 색조를 흉내내지 않는다 |
| 카피 | 쓰지 않는다 | 설명이 필요하면 화면이 잘못된 것이다 |
| 탭 이름 | 홈 · 장부 · 품목 · 정산 내역 · 아카이브 | '물건'은 장부 용어가 아니고, '정산 완료'는 미정산분을 가린다 |
| 첫 화면 갈림길 | 바로 나누기 / 팀 장부 | 가입 없이 계산하거나, 로그인해서 팀 장부로 들어가거나 |
| 팀 | 한 계정이 팀을 여럿 가진다 | 수업이 둘이면 팀도 둘이다 |
| 금액 저장 | 통화의 최소 단위 정수 | 소수 두 자리 통화에서도 1센트가 새지 않는다 |

### 파생 규칙 (구현하면서 드러난 것)

- **보정·환불 항목은 원본의 부담 구조를 그대로 물려받아야 한다.**
  4인이 나눠 낸 지출을 5인에게 환급하면 잔액이 남는다. 엔진·UI·DB 트리거 셋 다 강제한다.
- **검산은 송금 단위가 아니라 사람 단위여야 성립한다.**
  §14.2의 예시는 송금이 한 건뿐인 2인 상황을 가정한다. 한 사람이 여러 명에게서 받을 때는
  그 사람의 모든 송금·수령을 함께 보여줘야 `결제액 ± 이동 = 부담액`이 닫힌다.
- **나머지 1원은 버리지도 반올림하지도 않는다.**
  명단 순서대로 1원씩 배분하고 UI에 `7,166 (+1)`처럼 드러낸다. 명단 순서가 배분 순서라서
  `members.sort_order`와 `expenses.team_member_ids` 배열 순서가 계산 결과를 결정한다.

## 검증되는 불변식

`scripts/simulate.ts` — 21개

- 모든 Expense에서 지분의 합 = 금액 (원 단위, 음수 금액 포함)
- 어떤 Expense 집합에서도 balance 총합 = 0
- 총액 = 공동 정산 대상 + 개인 귀속
- 개인 귀속(결제자 = 귀속자)은 공동 정산 영향 0, 총지출에는 포함
- 개인 귀속(결제자 ≠ 귀속자)은 귀속자 채무로 반영
- 송금을 모두 실행하면 전원 balance = 0, 송금 횟수 ≤ 인원수 − 1
- 총지출 = 정산 완료 + 미정산, 중간 정산 후에도 Expense 원본 보존
- 사이클별 balance의 합 = 전체 기간 balance (누적 모델 연속성)
- 팀원이 나중에 합류해도 과거 정산 결과가 바뀌지 않음
- 이미 정산된 지출의 보정이 원본을 건드리지 않음

`supabase/tests/guards_test.sql` — 25개 (PostgreSQL 16에서 실제 실행 확인)

- 정산된 지출은 수정·삭제 불가, 확정 snapshot 변경 불가
- 한 지출은 한 정산에만 들어감
- 결제자·부담자·귀속자는 그 지출의 명단 안에 있어야 함
- 보정 항목의 부담 구조가 원본과 다르면 거부
- 환불 금액은 반드시 음수, 보정의 보정은 불가
- public 스키마 전 테이블 RLS 활성, anon 기본 거부
- 송금 완료는 받은 사람만 확인 가능, 확인된 송금은 되돌릴 수 없음
- 확인된 송금이 하나라도 있으면 정산 취소 불가
- 지출이 있는 장부의 통화는 변경 불가, 빈 장부는 가능, 없는 통화 코드는 거부

## 접근 모델

브라우저는 DB에 직접 붙지 않는다.

```
브라우저 → Next.js 서버 액션 → (service_role) → Postgres
```

초대 링크 방식이라 "로그인한 사용자"만으로는 권한을 표현할 수 없다. 토큰 접근을 RLS 정책으로
푸는 대신 검증 지점을 서버 액션 한 곳에 모았다. `anon`/`authenticated` 역할에는 정책을 주지
않아 기본 거부 상태다. `service_role` 키는 서버 전용 환경변수로만 쓴다.

## 결제와 공유의 실제 가능 범위

확인한 사실이다. 여기를 잘못 알고 설계하면 나중에 크게 손봐야 한다.

- **카카오페이는 외부 개발자에게 P2P 송금 API를 주지 않는다.** 공식 답변이 명시적이다.
  카카오톡 안의 "정산하기"는 카카오 내부 기능이지 열려 있는 API가 아니다.
  카카오페이가 외부에 제공하는 것은 가맹점 결제 API뿐이다.
- **네이버페이도 같다.** 가맹점 결제 연동만 있고 개인 간 송금 API는 없다.
- **카카오톡 공유는 검수 없이 쓸 수 있다.** 사용자가 보낼 채팅방을 직접 고르므로
  단톡방이든 개인톡이든 갈 수 있다. §17이 말한 Notification / Distribution Layer가 이것이다.
- **친구에게 메시지 보내기 API**는 비즈니스 검수가 필요하고 승인 전에는 하루 30건 제한이다.
  팀플 규모에는 과하다.

그래서 송금 자체는 앱 밖에서 사람이 한다. Ledger는 누구에게 얼마를 보내야 하는지 정확히
알려주고, 받은 사람이 확인해서 닫는다. API 없이 마찰을 가장 크게 줄이는 방법은
**팀원별 계좌번호를 저장해 두고 복사 버튼을 주는 것**이다. 아직 만들지 않았다.

## 아카이브

프로젝트가 끝나도 장부는 지워지지 않는다. 구조적으로 그렇게 되어 있다.

- 지출과 정산에 삭제 경로가 없다. 정산에 들어간 지출은 트리거가 UPDATE·DELETE를 막는다.
- `teams.owner_id`가 `on delete restrict`라, 장부를 만든 사람이 계정을 지워도 팀은 남는다.
- 프로젝트 종료는 `ledgers.archived_at`을 세우는 것이지 무엇을 지우는 게 아니다.

밖으로 꺼내는 길은 세 갈래로 본다.

1. **내보내기 (CSV / JSON / Markdown)** — 먼저 만들 것. 어디로든 갈 수 있는 형태가 우선이다.
2. **노션** — 공식 API가 있어서 장부를 데이터베이스로 밀어 넣는 것이 현실적이다. 그다음 순서.
3. **피그마** — 데이터의 목적지가 아니다. REST API는 읽기 중심이고 파일 생성은 플러그인 영역이라
   따로 프로젝트 하나가 된다. 아카이브를 그림으로 남기고 싶다면 인쇄가 더 빠르고 정확하다.
   그래서 인쇄용 스타일시트를 넣어 두었다. 아카이브 화면을 그대로 인쇄하면 종이 장부가 된다.

## 앱 골대 (Next.js + Supabase)

```
app/
  layout.tsx                 시각 시스템(globals.css) 로드
  page.tsx                   첫 화면 — 바로 나누기 / 팀 장부 두 갈림길
  QuickSplit.tsx             빠른 N빵 계산기 (팀 장부와 같은 엔진을 쓴다)
  AdSlot.tsx                 광고 슬롯 — 품목·아카이브에만 넣는다
  login/page.tsx             이메일 매직링크 / 카카오 로그인
  auth/callback/route.ts     로그인 돌아오는 자리
  teams/page.tsx             내 장부 목록 (수업이 둘이면 팀도 둘)
  teams/new/page.tsx         팀과 첫 장부 만들기 — 통화는 여기서만 정한다
  join/[token]/page.tsx      초대 링크 → 본인 선택 → 서명 쿠키 발급
  l/[ledgerId]/page.tsx      장부 홈
  actions/auth.ts            로그인 · 로그아웃
  actions/teams.ts           팀·장부 만들기, 내 장부 목록, 초대 링크
  actions/ledger.ts          지출·보정·환불·정산·취소·송금 확인
middleware.ts                세션 갱신만 한다 (권한 판정은 access.ts)
lib/
  access.ts                  초대 토큰 검증, 서명 쿠키, requireLedgerAccess
  db/client.ts               service_role 클라이언트 (server-only)
  db/repo.ts                 DB ↔ 도메인. 계산은 하지 않는다
  db/mapping.ts              row ↔ 도메인 타입
  domain/                    정산 엔진 (프레임워크 무관)
```

계층 규칙은 하나다. **계산은 `domain/`, 저장은 `db/repo.ts`, 권한은 `access.ts`.**
서버 액션은 셋을 잇고 오류를 사람 말로 바꾸는 일만 한다.

### 네가 해야 하는 것

키는 대화에 붙여넣지 말고 `.env.local`에만 넣는다.

**1. Supabase**
- 프로젝트를 만들고 `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`,
  `SUPABASE_SERVICE_ROLE_KEY`를 복사한다
- `supabase db push`로 마이그레이션 6개를 올린다
- Authentication > Providers 에서 Email을 켠다

**2. 카카오 로그인**
- [카카오 개발자센터](https://developers.kakao.com)에서 앱을 만든다
- 카카오 로그인을 활성화하고, Redirect URI에 Supabase가 알려주는 콜백 주소를 넣는다
  (`https://<프로젝트>.supabase.co/auth/v1/callback`)
- Supabase의 Kakao provider에 REST API 키와 Client Secret을 넣는다
- **비즈앱 전환은 하지 않아도 된다.** 이메일을 받지 않고 카카오 고유 ID로만 식별한다

**3. 카카오톡 공유**
- 같은 앱의 JavaScript 키를 `NEXT_PUBLIC_KAKAO_JS_KEY`에 넣는다
- 플랫폼 > Web 에 배포 도메인(`https://teamledger.net`)을 등록한다
- 검수는 필요 없다

### 좁은 화면

이 서비스는 폰에서 가장 많이 열린다. 정산 링크가 카카오톡으로 오가고, 받은
사람은 대개 폰으로 누른다. 그런데 장부는 원래 넓은 종이다. 여덟 칸을
350픽셀에 밀어 넣으면 글자가 세로로 접혀 "현/우"가 된다.

그래서 좁히지 않고 **접는다**. 640px 아래에서:

- 장부(`table.book.entries`)는 날짜·항목·금액만 남긴다. 전표 번호와 결제한
  사람과 부담은 줄을 눌렀을 때 펴지는 자리에 이미 있다.
- 검산 표(`.balances`)는 결제·부담을 접고 결과만 남긴다.
- 송금(`.transfers`)·초대 링크(`.invites`)·팀원(`.members`) 줄은 표를 접어
  세로로 쌓는다. 옆으로 늘어놓으면 계좌가 화면 밖으로 나가고 그 뒤의
  '보냈어요'가 같이 밀려 나간다. 폰에서 제일 많이 누르는 단추다.
- 탭은 두 줄까지 접히고 '지출 기입'은 아래에 한 줄로 눕는다.

칸을 접는 규칙은 표마다 붙인 이름(`entries`·`balances`·`transfers`·`invites`
·`members`)에만 건다. 같은 `book` 표를 여러 화면이 쓰기 때문에, 이름 없이
`nth-child`로 접으면 엉뚱한 화면에서 엉뚱한 칸이 사라진다.

입력칸 글자는 `pointer:coarse`에서 16px로 키운다. iOS는 그보다 작은 입력칸에
손을 대면 화면을 확대하고, 확대되면 그 뒤로 모든 것이 어긋나 보인다.

### 도메인

`teamledger.net`.

`.net`을 고른 이유는 값이 평평해서다. 프리미엄 등급이 없어 사전에 있는 단어가
들어가도 값을 올려 받지 않는다. 짧은 `ledger.day`는 등록기관이 프리미엄으로
잡아 매년 $64.93이었고, `ledger.studio`·`ledgerstudio.com`은 되팔이 업체가
쥐고 있었다.

주소는 이 서비스에서 링크의 수명이다. 정산 링크가 카카오톡 대화방에 몇 년이고
남아 있고, 그 링크는 도메인이 살아 있는 동안만 열린다. 그래서 셋을 지킨다.

- 여러 해를 한 번에 등록한다
- 자동 갱신과 도메인 잠금을 켠다
- 주소를 옮기지 않는다. 옮겨야 한다면 옛 주소를 버리지 말고 새 주소로 넘긴다

코드에는 도메인이 박혀 있지 않다. 초대 링크와 로그인 콜백은 요청이 들어온
주소에서 그때그때 만든다(`app/l/[ledgerId]/team/page.tsx`,
`app/auth/callback/route.ts`). 그래서 도메인을 바꿔도 코드는 고칠 것이 없고,
깨지는 것은 이미 나간 링크뿐이다.

**4. 영수증 분석**
- `ANTHROPIC_API_KEY`를 넣는다

**5. 광고**
- 실제 도메인에 배포하고 애드센스 심사를 통과해야 한다
- `NEXT_PUBLIC_ADSENSE_CLIENT`, `NEXT_PUBLIC_ADSENSE_SLOT`을 넣으면 슬롯이 켜진다
- 비어 있으면 슬롯 자체가 렌더되지 않고, `/ads.txt`도 404를 돌려준다.
  빈 ads.txt는 "아무에게도 권한이 없다"는 뜻이라 없느니만 못하다
- `/ads.txt`는 게시자 ID에서 자동으로 만들어진다. 파일로 따로 두지 않는다 —
  같은 번호가 두 군데 있으면 하나만 고쳤을 때 조용히 어긋난다
- 개인정보 처리방침은 `/privacy`에 있다 (애드센스 요구사항이자, 남의 계좌를
  맡아 두는 쪽의 최소한이다)
- **자동 광고(Auto ads)는 켜지 않는다.** 켜면 구글이 화면을 골라 광고를 끼워
  넣고, 그러면 정산 금액 옆에도 광고가 붙는다

### 광고 배치 규칙

`app/AdSlot.tsx`는 **품목과 아카이브 화면에만** 넣는다.
홈 · 장부 · 정산 내역 · 지출 기입에는 넣지 않는다.

그 화면들에는 누가 누구에게 얼마를 보내야 하는지가 적혀 있다. 정산 금액 옆에
서드파티 광고가 붙으면 §13.1이 요구하는 신뢰가 깨지고, 광고 스크립트가 그 페이지에서
트래킹을 시작한다. 컴포넌트 맨 위에 같은 내용을 주석으로 적어 두었다.

### 인증

신분이 두 가지고, 둘 다 `lib/access.ts` 한 곳에서 판정한다.

| 신분 | 어떻게 들어오나 | 판정 |
| --- | --- | --- |
| 장부를 만든 사람 | 이메일 매직링크 또는 카카오 | Supabase Auth 세션 |

`requireLedgerAccess`는 어느 쪽으로 들어왔든 같은 `Pass`를 돌려준다.
모든 서버 액션의 첫 줄이 이 함수다.

### 시각 시스템

순수한 웹의 검정, 흰색, 파랑만 쓴다. 종이 질감이나 색조를 흉내내지 않는다.
아날로그 장부의 물성은 색이 아니라 **구조**에서 나온다.

- 금액 칸을 감싸는 세로 괘선 — 장부를 장부로 보이게 하는 건 가로줄이 아니라 이 선이다
- 전표 번호 — 각 줄을 번호로 참조한다
- 이중 마감선 — 정산이 확정된 지점을 구획한다
- 인쇄용 스타일시트 — 아카이브를 그대로 인쇄하면 종이 장부가 된다

로고는 글자와 그 아래 이중선뿐이다. 회계에서 합계를 낸 숫자에 긋는 이중선을 그대로 쓴다.

**카피를 쓰지 않는다.** 첫 화면에는 설명 문장이 하나도 없다. 라벨, 숫자, 조작만 있다.
다른 화면도 같다. 설명이 필요하다고 느껴지면 화면이 잘못된 것이지 문장이 없는 것이 아니다.
구분자로 가운뎃점을 쓰지 않는다. 한 칸에는 한 덩어리만 넣고 나머지는 표의 열이 맡는다.

### 완료 도장

정산이 확정된 자리에는 고무도장이 찍힌다. 장부의 마감선, 확정된 정산 블록,
전부 정산된 아카이브 세 곳이다.

도장은 두 종류다.

- **마감선과 확정된 정산** — 이중 테두리에 날짜가 붙은 큰 도장
- **장부의 각 줄** — 테두리 없이 글자만 찍히는 작은 도장. 줄마다 각도가 달라서
  한 번에 인쇄한 것처럼 보이지 않는다

고무도장은 반듯하게 찍히지 않는다는 것만 흉내 냈다. 번호에서 각도와 위치를 조금씩
어긋나게 뽑고, SVG 노이즈를 마스크로 씌워 잉크가 고르게 묻지 않게 했다.
색은 도장 잉크(`--stamp`) 하나를 따로 뒀다. 숫자가 아니라 종이 위에 얹힌 물건의
색이라서 `--debit`(보낼 돈)과 헷갈리지 않는다.

### 언어와 화폐

`lib/domain/money.ts` — 금액은 언제나 **그 통화의 최소 단위 정수**로 저장한다.
KRW는 1 = 1원, USD는 1 = 1센트. 그래서 정산 엔진은 통화를 몰라도 되고,
소수 두 자리 통화에서도 1센트가 새지 않는다. 표기할 때만 통화를 쓴다.

**환율은 쓰지 않는다.** 통화를 바꿔도 환산하지 않고, 저장된 정수를 어느 통화의
최소 단위로 읽을지만 바뀐다. `715050` → KRW면 ₩715,050, USD면 $7,150.50이다.

환산을 하지 않는 이유는 두 가지다.

1. 팀원은 그 통화로 실제로 돈을 냈다. 오늘 환율로 바꾼 숫자는 아무도 내지 않은 금액이라
   §13.1의 "머릿속으로 검산할 수 있어야 한다"가 깨진다.
2. 환율은 매일 바뀐다. 확정된 정산의 금액이 내일 달라지면 §28.4(확정 정산 불변)가 깨진다.

통화는 보기 설정이 아니라 **장부의 성질**이다. 그래서 통화를 바꾸면 지금 보고 있는
장부에만 적용된다. 팀마다 다른 통화를 쓸 수 있다.

**통화는 장부를 만들 때 정하고 그 뒤로는 잠긴다.** 지출이 한 건이라도 기입되면 바꿀 수 없다.
이미 32,500(원)이 들어 있는 장부를 USD로 바꾸면 같은 정수가 $325.00으로 읽히는데,
아무도 낸 적 없는 금액이 된다. `0005_currency.sql`의 트리거가 DB에서 막는다.

### 해외 결제

환율 API를 부르지 않는다. 카드로 결제하면 카드사가 이미 환산해서 청구하므로
그 청구액을 쓰면 된다.

| 칸 | 뜻 |
| --- | --- |
| `amount` | 장부 통화의 최소 단위 정수. **실제로 청구된 금액이고 정산은 이것으로 한다** |
| `original_currency` | 영수증에 적힌 통화 |
| `original_amount` | 영수증에 적힌 금액 (그 통화의 최소 단위 정수) |

AI는 영수증에서 금액과 함께 **통화도 읽는다.** 한국어 영수증이면 대개 원화지만
해외 결제 화면이면 다르므로, 읽어 온 통화를 폼에 띄우고 사용자가 확인한다.
읽어 온 통화가 장부 통화와 다르면 장부 통화 청구액을 묻는 칸이 하나 더 나온다.
그 값이 없으면 저장되지 않는다.

그 지출에 실제로 적용된 환율만 쓰는 셈이라, 나중에 환율이 변해도 장부는 흔들리지 않고
§28.4(확정 정산 불변)도 지켜진다.

언어는 한국어와 영어. 프로토타입은 화면을 그린 뒤 글자만 바꿔 끼우는 방식이라
실제 앱에서는 문자열마다 키를 두고 번역 파일을 따로 관리해야 한다.

### 장부 조작

- 날짜와 금액 열 머리를 누르면 정렬한다. 다시 누르면 방향이 뒤집힌다.
- **정렬해도 전표 번호는 기입 순서 그대로다.** 금액순으로 봐도 언제 적은 것인지 알 수 있다.
- **시간 순서가 아닐 때는 마감선을 그리지 않는다.** 마감선은 시간 위에서만 뜻이 있다.
  정산 여부는 상태 칸이 계속 알려 준다.
- 체크박스를 쉬프트를 누른 채 클릭하면 마지막으로 고른 줄과 이번 줄 사이가 한꺼번에 처리된다.
  기준은 지금 화면에 보이는 순서다.

### 정산

정산 버튼을 누르면 탭을 옮기지 않고 **송금 창**이 열린다. 브라우저가 이미 가진
`<dialog>`를 그대로 쓴다. 창 안에서 송금 목록을 확인하고 계산을 펼쳐 보고,
카카오톡으로 보내거나 확정한다. 확정한 정산은 목록에서 다시 보낼 수 있다.

### 송금 · 정산 취소

- 송금 완료는 **받은 사람만** 확인할 수 있다 (DB 트리거가 강제).
- 정산 취소는 **확인된 송금이 하나도 없을 때만** 가능하다.
  취소하면 그 지출들은 자동으로 미정산으로 돌아가고 다시 수정할 수 있게 된다.
- 이미 송금이 오간 정산은 잠긴다. 그때는 보정 항목으로 바로잡는다.
